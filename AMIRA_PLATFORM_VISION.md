## 1. Why this document exists

FinIQ is the first complete app produced by what we are starting to call the Amira platform. It was built through a deliberate but heavily manual process: write specs → three people each build the app independently → harvest the best parts → upgrade the spec → rebuild the merged version → run a compliance loop until it passes. That process worked — we have a working app on `main`, six days from a Mars MLT demo with Bruce Simpson — but it does not scale. The next ten apps cannot each consume three engineers and three months of bake-off.

This document does three things:

1. **Records what we actually did** for FinIQ — the specs, the builds, the merge, the polish — so anyone joining (human or bot) can reconstruct the lineage.
2. **Positions FinIQ inside the Amira platform** — what FinIQ is, what Amira is, how the relationship works, what comes after FinIQ.
3. **Proposes how OpenSpec collapses the spec stage** — what changes if we adopt it, what stays the same, and what the new "first day" of building app #2 looks like.

It is meant to be shared with the team AND read by the AI agents in our ecosystem so the flow is consistent regardless of which agent is invoked.

## Part 1 — How FinIQ was built

### 1.1 The problem we started with

Mars, Incorporated runs two separate AI-powered analytics tools today:

- **Period End Summary (PES)**. Transforms raw financial Excel data into AI-generated executive performance summaries. Six predefined KPIs (Organic Growth, MAC Shape %, A&CP Shape %, CE Shape %, Controllable Overhead Shape %, NCFO), three formats (Summary, What's Working Well, What's Not Working Well), Azure OpenAI GPT-4.1 backend, ~10–15s first generation.
- **Competitive Intelligence (CI)**. Ingests competitor earnings PDFs, generates themed summaries (organic growth, margins, projections, consumer trends, etc.), benchmarks Mars against a peer set, supports Q&A with citation links. Azure Document Intelligence + AI Search + Cosmos DB.

Both are useful. Neither talks to the other, neither does ad-hoc questions, neither is configurable by business users without engineering, and neither integrates with marketing analytics or forecasting. The PES six KPIs are hard-coded; if Bruce wants a seventh, an engineer ships code. The CI engine cannot answer "how did Mars's organic growth compare to Nestlé's last quarter?" without manual stitching.

FinIQ is the unified hub that consolidates both, adds an enterprise agent job board for ad-hoc work, opens the data to natural-language queries, and wires in cross-source intelligence (internal financials × external CI × marketing analytics × forecasting).

## Part 3 — The spec process, in painful detail

The current (manual) flow has four stages. Each one is doing real work; the question is which can be compressed and which cannot.

### 3.1 Stage A — Spec authoring

**Today**: Rajiv (or whoever) hand-writes a Word document. SRS v3.0 was generated by `generate_srs_final.py` (python-docx). v3.1 added Section 7 + FR4.5/4.6 + Appendix C. Frontend Design Guideline v1.0 written by Atlas, formatted by Rajiv. Synthetic data + schema reference produced as supporting artifacts.

**What Stage A actually produces**: a body of requirements (52 FRs grouped FR1–FR8), a design system, a data schema, and a glossary — all in Word format. No machine-readable structure beyond the document itself.

**Cost**: significant human time for the spec author, reviews from Bruce/Matt/Karthik on Mars side, multiple revisions. The Addendum A pattern (incremental amendments) was used once for the Databricks integration; the team then pivoted to "combine everything into one final unified SRS" because no code existed yet.

**Why this stage is hard to compress**: domain elicitation. Mars has 13-period fiscal years, Title Case Unit_Alias, dispersed analytics tools, six predefined PES KPIs, a peer set of ten competitors, RLS rules, RBAC needs, GBU hierarchy 11 levels deep. None of that comes from a single conversation. It has to be drawn out.

### 3.2 Stage B — Build

**Today**: three parallel agent builds against the same spec. Each builder picks their own tech stack and architecture. Each build runs for one to two weeks. Output: three independently-functioning apps with overlapping coverage and divergent strengths.

**What Stage B actually produces**: code, learnings, and (most importantly) *gaps in the spec made visible*. Voice, the ten-tab CI structure, Bloomberg-style data exploration, ProvenanceBadges, the QML "why" chip — none of these were in any version of the SRS. They emerged because three different operators interpreted the same spec differently and noticed what was missing.

**Cost**: heavy. Three engineers, three build environments, three apps, two weeks.

**Why this stage was a one-time exercise, not a process**: the discovery value is biggest the first time. Now that we have FinIQ's working code, its CLAUDE.md, its memory files, its compliance matrix, its bug audit, its SRS v3.1 — the gaps are largely known. Building three more financial apps would not surface much new. Building one app in a *new domain* (Supply Chain) might; building app #11 in financial-adjacent territory will not.

### 3.3 Stage C — Harvest and merge

**Today**: manual review of the three builds, a written merge plan (`FinIQ Merge Plan.docx` on Desktop), a new `merged` branch off Ale's repo, careful selection of components (Ale's UI base, Rajiv's CI tabs and header, our LLM/voice/job board/safety), schema rename to match real Databricks, and roughly twenty commits to land the merged version on `main`.

**What Stage C actually produces**: the unified codebase, AND the upgraded spec — because the merge forces explicit decisions about which interpretation of each requirement wins. The post-merge SRS would, if we wrote it now, be more precise than v3.1: "queries SHALL render as a chat message containing narrative + chart + table + provenance badge, with follow-up chips offering trend / variance / cross-reference paths."

**Cost**: moderate but unavoidable in this approach.

**Why this stage is mostly retired**: it only existed because of Stage B's parallelism. If Stage B produces one app instead of three, Stage C is just normal code review.

### 3.4 Stage D — Compliance loop

**Today**: an 80-item matrix (52 functional + 15 design + 6 CI/FMP + 7 technical) maintained as `compliance/compliance-matrix.json` (now superseded) and embedded in `BUILD_PROMPT.md`. Each item has a target (PASS / PARTIAL / FAIL) and a scoring rubric. The coding agent and a reviewer agent iterate against the matrix until the score plateaus. This is the Karpathy "automate the vibe" pattern — make the success criteria measurable, then optimize the model against them.

The Testing Agent SRS v1.1 formalized this with quantitative metrics: PES ≥ 95%, NL Queries ≥ 85%, Budget Variance ≥ 95%, overall ≥ 85%. 31 binary pass/fail criteria, 15 acceptance criteria.

**Current state**: 67.5/80 (84.4%). Remaining gaps are SQL parameterization (T1), data lineage (FR1.4), configurable KPIs (FR2.2), internal-external cross-ref (FR3.3 — actually mostly built but undercredited), WCAG accessibility (FR8.6), multi-turn context (FR4.2).

**What Stage D actually produces**: the polish that turns a credible V1 into something demoable to executives. It is also where the spec acquires teeth — items that are not measurable cannot be optimized, so the matrix forces the spec to commit.

**Why this stage stays**: it has no obvious replacement and is genuinely valuable. The output of Stage D is not just a better app, it is a stronger spec for the next app.

### 3.5 The artifacts we maintain (the durable ones)

Across all four stages, these artifacts are the things future apps will inherit:

| Artifact | Purpose | Who maintains |
|---|---|---|
| **SRS v3.1** | Functional and non-functional requirements, IEEE 830 format | Rajiv, with team review |

This is what the bots learn from. This is what app #2 starts with.

## Part 4 — OpenSpec, and what it changes

### 4.1 What OpenSpec is, technically

OpenSpec (https://github.com/Fission-AI/OpenSpec) is a lightweight specification-driven development framework for AI coding assistants. Distributed as an npm package (`@fission-ai/openspec`, requires Node ≥ 20.19), tool-agnostic (works with Claude Code, Cursor, Copilot, Windsurf, and ~20 other agents via slash commands).

**Two-folder anatomy**:

```
openspec/
├── specs/      # Source of truth — current agreed system behavior
└── changes/    # Each proposed change is a self-contained folder
```

**Specs are organized by domain**:

```
openspec/specs/
├── auth/spec.md
├── payments/spec.md
└── ui/spec.md
```

**Spec format** uses a fixed hierarchy and RFC 2119 keywords:

```markdown
# Auth Specification

## Purpose
Authentication and session management for the platform.

## Requirements

### Requirement: Email/password sign-in
The system SHALL allow users to authenticate via email and password.

#### Scenario: Valid credentials
- GIVEN a registered user with valid credentials
- WHEN they submit the sign-in form
- THEN they are redirected to the dashboard
- AND a session cookie is set
```

Specs describe **observable behavior**, not implementation. No class names, no framework choices, no step-by-step logic.

**Each change is a self-contained folder**:

```
openspec/changes/add-2fa/
├── proposal.md         # Intent, scope (in/out), approach
├── design.md           # Technical decisions, file changes
├── tasks.md            # Hierarchical checklist (1.1, 1.2, ...)
└── specs/              # DELTA specs by domain
    └── auth/spec.md    # ## ADDED Requirements / ## MODIFIED / ## REMOVED
```

The **delta system** is the key innovation. Changes never touch main specs directly. They specify additions, modifications, and removals. On `/opsx:archive`, the deltas merge into `openspec/specs/`, and the change folder moves to `openspec/changes/archive/2026-04-15-add-2fa/` with full audit trail. Multiple changes can touch the same domain without conflicts; resolution is by implementation order.

**Lifecycle commands** (Claude Code syntax):

| Command | What it does |
|---|---|
| `/opsx:propose <name>` | Creates a change folder with proposal + delta-specs + design + tasks in one shot |
| `/opsx:explore <topic>` | Investigates uncertain territory before committing artifacts |
| `/opsx:apply <name>` | Implements the tasks |
| `/opsx:verify <name>` | Validates completeness (all tasks done, scenarios covered), correctness (intent alignment, edge cases), coherence (design reflected in code) |
| `/opsx:archive <name>` | Merges deltas into specs, moves change folder to archive with timestamp |

Expanded profile adds `/opsx:new`, `/opsx:continue`, `/opsx:ff`, `/opsx:sync`, `/opsx:bulk-archive`, `/opsx:onboard`.

**Schema system** — and this is where it gets relevant for Amira — defines artifact types and their dependency graph as YAML. The default `spec-driven` schema is `proposal → specs → design → tasks → implement`. Dependencies are *enablers, not gates* — you can skip artifacts or reorder. Custom schemas are first-class. So a "Mars-finance-app" schema could declare additional artifacts like `compliance-matrix.md` and `data-schema.md` as required outputs.

### 4.2 What OpenSpec maps onto from FinIQ today

| FinIQ artifact (today, manual) | OpenSpec equivalent |
|---|---|
| SRS v3.1 sections FR1–FR8 grouped by domain | `openspec/specs/{ingestion,reports,ci,query,jobs,integration,admin,ui}/spec.md` — one file per FR group |
| SRS Addendum A (Databricks integration) | `openspec/changes/databricks-integration/specs/{ingestion,reports}/spec.md` with `## ADDED Requirements` blocks, archived on merge |
| Frontend Design Guideline v1.0 | `openspec/specs/design-system/spec.md` (or a custom artifact via schema) |
| 80-item compliance matrix in BUILD_PROMPT.md | The Scenarios under each Requirement become matrix items; `/opsx:verify` is the runner |
| Testing Agent SRS v1.1 quantitative metrics | Lives as scenario assertions: `THEN the response time SHALL be < 2s for cached queries` |
| `BUILD_PROMPT.md` 8 batches | `tasks.md` per change, dependency-ordered |
| CLAUDE.md / memory / Bug audits | Stays as-is — these are operational notes, not specs |

The translation is mostly mechanical. The hard part is committing to the discipline of "Requirements describe behavior, not implementation" — because some of the SRS today reads more like a design doc.

### 4.3 What OpenSpec automates

**Stage A (spec authoring)** is the stage OpenSpec changes most:

- The Word-doc round-trip disappears. Specs live in the repo as markdown, version-controlled with the code, diffable, machine-readable.
- The Addendum pattern stops being a manual exercise. Every change is a delta; archiving merges it.
- The compliance matrix stops being a separate document. Scenarios under each Requirement are the matrix items. `/opsx:verify` is the loop runner.
- Multiple agents (Asimov, Atlas, Air, Claude, Artemis) consume the same source-of-truth specs. No more "which version of the SRS did you read?"

**Stage B (build)** still happens, but on a single track. The bake-off retires for known domains. New domains may still warrant exploration — `/opsx:explore` is the lightweight version of the bake-off (investigate without committing artifacts).

**Stage C (merge)** essentially disappears for normal iteration. It only re-emerges when you genuinely have parallel teams on the same change — and the delta system handles that without manual reconciliation.

**Stage D (compliance loop)** stays, but the loop runs against `/opsx:verify` outputs instead of a hand-maintained matrix. The polish-then-update-spec pattern becomes natural.

### 4.4 What OpenSpec does NOT automate

This is important to be honest about:

- **Domain elicitation**. OpenSpec is a format, not an interviewer. Mars's 13-period fiscal year, Title Case Unit_Alias, etc. — none of that comes free. Someone still has to ask the right questions.
- **Architectural decisions**. The fact that voice should be inline in chat rather than a separate page (Rajiv's call), the choice of OpenAI over Anthropic (Mars constraint), the dual-mode pattern (security pushback) — these are human decisions informed by context OpenSpec does not have.
- **Discovery of missing requirements**. Voice, ten-tab CI, ProvenanceBadge, QML "why" chip — these came from building. OpenSpec records what you decide; it does not invent novel features.

This is where the **OpenSpec Agent** (the conversational layer on top of OpenSpec — see next section) becomes the interesting piece.

### 4.5 The OpenSpec Agent (a proposed Amira mini-agent)

The OpenSpec npm package gives you the format and the verbs. It does not give you a conversation. The proposal is to build an Amira mini-agent — call it the **Spec Agent** — whose job is to:

1. **Elicit** requirements from a user (Mars exec, internal stakeholder, or another agent) through guided conversation. Ask the kinds of follow-ups that turn "build me a supply chain dashboard" into 50 Functional Requirements.
2. **Reference the library** of prior apps (FinIQ specs, Health Data prototype, etc.) to surface implicit requirements. "Every Mars-finance app has needed RBAC, audit trail, RLS — should we include those?"
3. **Propose the spec** in OpenSpec format. Show the user the structured output and let them review/edit before commit.
4. **Suggest a schema**. For a financial app, suggest the Mars-finance schema (specs + design system + compliance matrix + data schema). For a logistics app, suggest a different one.
5. **Hand off** to the Amira platform's build orchestrator, which routes to the appropriate builder agent (or, if none exists yet, scaffolds a new mini-app from the spec).

Critical design constraint, drawn from the FinIQ experience: the Spec Agent should **propose alternatives, not converge on one**. Where the spec has degrees of freedom (single-page vs multi-tab CI; voice as page vs inline chat; KPI cards vs treemaps), the agent surfaces choices. This preserves what the bake-off gave us — diversity of interpretation — without requiring three full builds to get it.

### 4.6 What "learning from previous apps" actually means

The pitch of the Spec Agent is that it gets better as more apps are built. To make that real, we need to be specific about what gets learned and where it lives:

| Learning type | Source | Where it goes |
|---|---|---|
| Domain idioms (Mars 13-period FY, Title Case names) | Real-world data discovery | Reference specs and schema files in the platform's library |
| Standard patterns (RBAC, RLS, audit trails) | Prior FRs that recurred across apps | Schema templates the Spec Agent can suggest |
| Anti-patterns (LLM struggles with `ROUND(AVG())`) | Bug audits and fix histories | Guardrails injected into spec scenarios |
| UX templates (narrative + chart + table + provenance) | Architecture decisions that worked | Reusable Requirement blocks in the platform's library |
| Quantitative thresholds (PES ≥ 95%) | Testing Agent SRS metrics | Default scenarios in compliance schemas |

Some of this lives in OpenSpec's own format. Some lives in the platform's mini-agent library. Some lives in CLAUDE.md / memory and is consulted at elicitation time. The Spec Agent is the integration point.

## Part 5 — The future flow, walked through

To make this concrete, here is what building Mini-App #2 — say a Supply Chain dashboard for Mars Petcare — looks like under the proposed flow.

### Day 1: Conversation

A Mars stakeholder (or Bill / Bruce / a brand manager) opens the Amira platform and says something like: *"We need a supply chain dashboard for Petcare. It should show supplier risk, inventory levels, expected commodity-cost impact, and tie back to the financial impact on margins."*

The Spec Agent engages:

- "What time horizon? Daily, weekly, monthly?"
- "Which suppliers — top 10 by spend, all tier-1, or filterable?"
- "Inventory at the SKU level or the product family level?"
- "For commodity costs, do you want to integrate with the QML market data we already use in FinIQ? That would let you correlate cocoa futures with Petcare margin pressure."
- "RBAC: same model as FinIQ (4 roles, peer groups)?"
- "Cross-reference with FinIQ's financial data — yes or no?"

The agent pulls from the FinIQ library: it knows about RBAC (FR7), the unified chat-first interface, the provenance badge pattern, the dual-mode (real/simulated) requirement, the OpenAI-only LLM constraint. It surfaces these as default suggestions and lets the user accept/modify/decline.

After ~30–60 minutes of dialogue, the Spec Agent emits a structured OpenSpec layout:

```
openspec/specs/
├── ingestion/spec.md
├── supplier-risk/spec.md
├── inventory/spec.md
├── commodity-impact/spec.md
├── financial-impact/spec.md   # cross-references FinIQ via A2A
├── ui/spec.md
└── design-system/spec.md      # inherited from FinIQ
```

The user reviews. Edits a few requirements. Commits.

### Day 2–3: Build

The Amira platform takes the spec and routes it. Possibilities:

1. **An existing mini-agent can answer most of it.** FinIQ's `finiq-data-agent` already handles financial cross-references. The platform spawns a thin wrapper mini-app that orchestrates calls.
2. **A new mini-app is needed.** The platform invokes the build orchestrator (the role Cesar's runtime plays). It scaffolds the Next.js + Tailwind monolith (same template as FinIQ's Ale-base), wires in the design system, adds the LLM query pipeline, and starts implementing tasks from `tasks.md`.

Either way, no human writes boilerplate. A working V1 emerges in 2–3 days, not 2–3 weeks.

### Day 4–7: Polish

The compliance loop runs. `/opsx:verify` scores the build against the scenarios in each spec. Below-threshold items become tasks for a follow-up change. The build agent iterates. The score climbs. New gaps surface (e.g., "supplier risk needs a heat-map view that wasn't in the spec") — these become new changes via `/opsx:propose`, with delta specs that get archived as the loop completes.

### Day 8: Demo

Stakeholder gets a polished V1, around 85%+ on its compliance matrix, deployed in the Amira tenancy, with the cross-reference to FinIQ already wired (because the Spec Agent knew to specify the A2A handshake).

The bake-off — three teams, three months — does not happen. The polished V1 emerges in roughly one week. The Spec Agent learned from FinIQ's matrix what to optimize against. The platform reused FinIQ's design system, RBAC module, dual-mode pattern, provenance badges. The new app contributes back: its `commodity-impact/spec.md` becomes part of the library, available to the next app.

### And the one after

App #3 (say, the Health Data app for vet-clinic dental scans) starts even faster. The Spec Agent now has two prior apps to draw from. It knows, for example, that "every Mars app needs a Help page with a guided tour." It knows the QML enrichment pattern works. It knows OpenAI is the LLM constraint. It does not have to be told.

That is the factory.

## Appendix B — For the bots

This section is addressed to AI agents that consume this document: Asimov (Rajiv), Atlas (Alessandro), Artemis / OpenClaw (Farzaneh's build agent), Air (Bill), Claude Code (general), and the future Spec Agent.

**When you read this document, treat the following as canonical for the Amira platform**:

1. **FinIQ is not the platform.** FinIQ is a mini-app. The platform is Cesar's runtime + the spec process described here.
2. **The bake-off is over.** Do not propose three parallel builds for new apps as a default. Use `/opsx:explore` for genuinely unknown territory; otherwise build one tracked V1.
3. **Specs live in OpenSpec format going forward.** When asked to write specs for a new app, produce `openspec/specs/{domain}/spec.md` files with RFC 2119 requirements and Given/When/Then scenarios. Do not produce Word documents unless explicitly asked.
4. **Specs describe behavior, not implementation.** No class names, no framework choices, no step-by-step logic in the spec. Those go in `design.md` and `tasks.md`.
5. **Reuse the FinIQ library.** The design system, RBAC pattern, provenance badge pattern, dual-mode pattern, voice agent pattern, QML enrichment pattern, and OpenAI-only LLM constraint are defaults for Mars apps. Suggest them by default; only omit when the user declines.
6. **The compliance matrix is the success criterion.** When implementing, optimize against `/opsx:verify` scores. When proposing, attach scenarios that make verification possible.
7. **Mars-facing language**: never use "replace" or "fragmented." Use "augment," "consolidate," "evolve," "enhance," "dispersed," "separate." No timelines, no cost estimates in client-facing artifacts.
8. **Confidential**: the QML / Q.Enterprise API key and documentation are not to be reproduced in code, commits, or shared artifacts.
9. **OpenAI only** for LLM calls in production. Anthropic models are ruled out by Mars's Azure AI Foundry constraints.
10. **Cross-app A2A is the endgame** but not yet wired. When specifying inter-app calls, mark them as `// pending A2A` and keep the local fallback.

When in doubt, consult `CLAUDE.md` and the `memory/` files in the Claude Code project directory, or ask the operator.
